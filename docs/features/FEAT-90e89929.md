## Technical Approach

### 1. Workflow TOML Rewrites

**MODE-A.toml** — restructure from 9 steps to 6 steps:
- Remove steps: `implement-sdd`, `code-review`, `test-run`, `verify`
- Add step: `implement-verify` (replaces all four removed steps)
- `req-create` and `finish` remain as-is (identical step IDs and gate patterns)
- `write-plan` gains a new `state_set` gate: `review_plan_spec_consistency_passed`
- All `prompt_file` values change from flat filenames to `mode-a/{step-id}.md`
- No `[[steps.fail_route]]` changes needed (MODE-A had none)

**MODE-B.toml** — structure stays at 7 steps:
- All inline `prompt` fields replaced with `prompt_file = "mode-b/{step-id}.md"`
- No step ID or gate changes
- No fail-route changes
- Cross-workflow `next = "MODE-A:write-plan"` on `debug-finish` preserved

Both TOMLs use only existing `[[steps]]`, `prompt_file`, `gates`, `next`, and `[[steps.fail_route]]` fields. No schema changes.

### 2. Prompt File Migration

Create two subdirectories under `.devflow/prompts/`:

- `.devflow/prompts/mode-a/` — 6 files: `req-create.md`, `req-approve.md`, `brainstorm.md`, `write-plan.md`, `implement-verify.md`, `finish.md`
- `.devflow/prompts/mode-b/` — 7 files: `debug-root-cause.md`, `debug-pattern.md`, `debug-hypothesis.md`, `debug-fix.md`, `debug-question.md`, `debug-verify.md`, `debug-finish.md`

All written in English. Each file defines: role (main agent or subagent), input files to read, output files to create, step-by-step procedure, and expected gate conditions. Autonomous steps include subagent dispatch patterns and review-loop instructions. Human-gated steps (`req-approve`, `brainstorm`, `debug-question`) explicitly state that the agent must wait for user approval.

The `implement-verify.md` prompt is the largest new file — it encodes the full 5-round topology-sorted parallel subagent loop with TDD, code review, unified testing, and evidence collection.

**Deleted** (11 flat prompt files no longer referenced by any TOML):
- `req-create.md`, `brainstorm.md`, `write-plan.md`, `implement-sdd.md`, `code-review.md`, `verify.md`, `finish.md`
- `debug-root-cause.md`, `debug-pattern.md`, `debug-hypothesis.md`, `debug-fix.md`

Existing `load_prompt()` in `workflow_parser.py` resolves `prompt_file` relative to `.devflow/prompts/` first, then the workflow directory — this resolution order naturally picks up `mode-a/implement-verify.md` without any engine change.

## Architecture

### Execution Model: Architect/Subagent

The v3.0 redesign introduces a two-tier execution model with no engine changes:

| Tier | Role | Model | Responsibilities |
|------|------|-------|-----------------|
| Main Agent | Architect | Current session model (Sonnet/Opus) | Reads step prompt, designs approach, decomposes work into independent tasks, dispatches subagents, reviews results, loops on failure |
| Subagents | Workers | Haiku (per subagent dispatch) | File I/O, code editing, test execution, search, document drafting, TDD implementation, evidence collection |

The main agent remains in the session. Subagents are spawned in parallel using the `subagent-driven-development` skill or `dispatching-parallel-agents` skill, each running a Haiku-powered Claude Code instance against an isolated task.

### `implement-verify` Inner Loop

The implement-verify step encompasses what was previously four separate steps. The main agent orchestrates this loop:

```
Round 1: Topology-sorted parallel implementation
  ├─ 1a. Read PLAN-{run_id}.md, analyze task dependency graph
  ├─ 1b. Identify batch: tasks with zero unsatisfied dependencies
  ├─ 1c. Dispatch parallel Haiku subagents (one per task, each TDD)
  ├─ 1d. Each subagent completes -> dispatch review subagent
  ├─ 1e. Review fails -> dispatch fix subagent -> re-review -> loop
  ├─ 1f. Batch done -> next batch until all tasks complete

Round 2: Unified testing
  ├─ 2a. Run {test_command}
  ├─ 2b. All pass -> Verification
  ├─ 2c. Failures exist -> analyze topology, decompose into fix tasks
  ├─ 2d. Dispatch fix subagents -> goto Round 1
  ├─ 2e. Max 5 rounds; if problem count not monotonically decreasing -> human

Verification:
  ├─ V1. For each acceptance criterion: IDENTIFY -> RUN -> READ -> VERIFY -> CLAIM
  ├─ V2. Generate docs/evidence/EVIDENCE-{run_id}.md with raw output
  ├─ V3. devflow set review_implement_verify_passed true
  └─ V4. devflow done
```

### Gate Usage

Gates remain the sole mechanism for progression. The `implement-verify` step has two gates:
1. `command_success:{test_command}` — all tests must pass
2. `file_exists:docs/evidence/EVIDENCE-{run_id}.md` — evidence document must exist

These are checked by `gate_checker.py` during `engine.advance()`, exactly as all other gates are. The inner-loop complexity lives in the prompt, not in engine code.

The `write-plan` step adds `state_set:review_plan_spec_consistency_passed`, set by the main agent after the plan-spec consistency review subagent passes. This uses the existing `state_set` gate type — no new gate implementation needed.

### Autonomous vs Human Steps

| Step | Autonomy | Reason |
|------|----------|--------|
| MODE-A req-create | Auto | Document generation, no judgment call |
| MODE-A req-approve | **Human** | Requirements define scope — needs explicit user sign-off |
| MODE-A brainstorm | **Human** | User chooses design direction |
| MODE-A write-plan | Auto | Subagent-driven plan-spec consistency review loops |
| MODE-A implement-verify | Auto | Inner loops auto-recover; max rounds + convergence check prevent infinite loops |
| MODE-A finish | Auto | Gate-checked completion |
| All MODE-B steps | Auto | Except debug-question |
| MODE-B debug-question | **Human** | After 3+ consecutive fix failures — user decides refactor/fix/abandon |
