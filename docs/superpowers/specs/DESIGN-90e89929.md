## Summary

Three approaches were considered: A (minimal changes — keep flat prompts, leave MODE-A at 9 steps), B (archive old files but keep structure largely intact), and C (aggressive refactor with mode-specific prompt directories, unified naming, and a merged implement-verify step). Approach C was chosen because it delivers the clearest organizational separation, eliminates redundancy in MODE-A's execution phase, and sets a consistent naming convention that scales to future workflow modes without further restructuring.

## Key Design Decisions

### 6-Step MODE-A with Merged implement-verify
MODE-A is reduced from 9 steps to 6 by merging `implement-sdd`, `code-review`, `test-run`, and `verify` into a single `implement-verify` step. This eliminates artificial handoffs between implementation phases and lets a topology-sorted inner loop handle the sub-steps internally. The step sequence is: `req-create` (auto) → `req-approve` (human) → `brainstorm` (human) → `write-plan` (auto) → `implement-verify` (auto) → `finish` (auto).

### 7-Step MODE-B, Structure Unchanged
MODE-B retains its existing 7-step structure (`debug-root-cause` through `debug-finish`) with fail routes and the cross-workflow transition to MODE-A:write-plan preserved. The `debug-question` human gate is kept as-is. Only prompt file organization changes.

### `mode-a/` and `mode-b/` Prompt Directories
All prompts are organized under `.devflow/prompts/mode-a/` and `.devflow/prompts/mode-b/` respectively, with the naming convention `{mode-dir}/{step-id}.md`. This replaces the flat `prompts/` directory. The existing `load_prompt()` resolution logic already searches `.devflow/prompts/` first, so no engine changes are required.

### Subagent-Driven Execution Model
The main agent (current session model) handles design, planning, task decomposition, and review only. All operational actions (file I/O, code editing, test execution, search) are delegated to parallel Haiku subagents. Each subagent returns results for main-agent review; failed reviews trigger a fix subagent loop until passing.

### Autonomous Progression with 3 Human Gates
All steps progress autonomously except three that require explicit human confirmation: `req-approve` (approve requirements), `brainstorm` (choose design approach), and `debug-question` (decide refactor/fix/abandon after 3+ consecutive fix failures).

### No Engine Changes
The `implement-verify` loop and plan-spec consistency review use the existing `state_set` gate type (`review_plan_spec_consistency_passed`, `review_implement_verify_passed`). No changes are needed to `gate_checker.py`, `workflow_parser.py`, or `workflow_engine.py`. No new TOML schema fields are introduced.

### implement-verify Inner Loop
The merged step follows a structured algorithm: Round 1 processes topology-sorted batches of independent tasks via parallel Haiku subagents (each following TDD with review/fix loops). Round 2 runs unified testing. On failure, the loop decomposes failures into new fix tasks and repeats. Verification generates an evidence document with raw command output. Max 5 rounds; if problem count does not decrease monotonically, the loop pauses for human intervention.
